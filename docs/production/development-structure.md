# 游戏开发全项目目录规范

日期：2026-11-22  
状态：基础目录迁移与 README 已落地；细分目录和程序分层按实际工作逐步推进。

本规范覆盖游戏之外的整体企划、玩法设计、3D原型、美术、素材、音乐音效、数值、研发、测试和发布。程序内部架构另见[单机海战游戏架构规划](../technical/architecture.md)。

行业没有唯一强制的目录标准。这里采用适合独立开发和小团队的组织方式：按工作领域划分，区分制作源文件与运行资源，明确唯一数据来源和发布边界。

## 2. 企划与设计文档

### 2.1 整体企划：`docs\planning`

回答“为什么做、为谁做、做多大”：

- `vision.md`：游戏愿景、目标体验和定位。
- `pitch.md`：简明介绍、核心卖点和展示方案。
- `scope.md`：首版范围、明确不做的内容和后续方向。
- `audience.md`：目标玩家与使用场景，不收集个人资料。
- `roadmap.md`：阶段计划和交付目标。
- `risks.md`：技术、内容规模、许可和制作风险。

对本项目，定位应明确为单机海战游戏，而不是完整还原原版网游。不要把已有图鉴数量直接写成已实现舰船数量。

### 2.2 游戏设计：`docs\game-design`

回答“玩家如何玩、规则是什么”：

- `gdd.md`：游戏设计总纲，连接各专题，不堆入全部细节。
- `core-loop.md`：港口、配装、任务、战斗、结算的核心循环。
- `controls.md`：键位、鼠标、镜头和交互规则。
- `fleet-and-formation.md`：旗舰、舰队角色、阵型和命令。
- `combat.md`：炮控、弹道、命中、毁伤和胜负条件。
- `missions.md`：任务类型、目标与关卡组织。
- `balance.md`：数值设计原则、公式含义和版本策略。
- `progression.md`：后续成长与经济设计；未实现时明确标记。

企划不代替玩法规则，玩法文档也不代替实际数值表。

### 2.3 美术、音频与技术设计

| 目录 | 推荐文档 | 内容 |
|---|---|---|
| `docs\art-direction` | `style-guide.md` | 色彩、比例、时代感、视觉参考与原创方向 |
| `docs\art-direction` | `model-standard.md` | 单位、坐标、前向、原点、节点、材质与LOD |
| `docs\art-direction` | `ui-style.md` | 仪表、字体、图标、布局与分辨率规则 |
| `docs\audio-direction` | `audio-design.md` | 音乐场景、音效层次、空间声与氛围 |
| `docs\audio-direction` | `mixing-guide.md` | 总线、循环、响度、命名与导出要求 |
| `docs\technical` | `architecture.md` | 模块、依赖、模拟与表现边界 |
| `docs\technical` | `data-standard.md` | 数据格式、单位、ID、版本与来源 |
| `docs\technical` | `asset-pipeline.md` | 素材入库、加工、校验与运行包生成 |
| `docs\technical` | `save-and-replay.md` | 存档、回放与兼容性 |
| `docs\qa` | `test-plan.md` | 功能、数值、资源、性能与兼容性测试 |

现有架构文档已迁入 `docs\technical`，本目录规范位于 `docs\production`；入口统一由项目根 README 和各领域 README 提供。

### 2.4 制作管理：`docs\production`

存放里程碑、功能验收清单、会议结论和决策记录。任务状态最好使用统一任务系统，文档保留重要结论，避免多份清单互相矛盾。

合同、付款材料、非公开授权邮件和个人联系信息不放入公开仓库，应在独立的私有管理空间保存。项目内只保留可公开的许可摘要与来源引用。

## 3. 原型与正式资产的区别

`prototypes` 用于回答尚未确定的问题，不是正式资产仓库：

| 原型 | 验证目标 |
|---|---|
| `prototypes\gameplay` | 接敌时间、散布、队形、任务节奏 |
| `prototypes\3d` | 舰船灰模、尺寸、炮位、海面、镜头、LOD |
| `prototypes\ui` | 船坞流程、配装窗口、仪表布局 |
| `prototypes\audio` | 炮声层次、远近声、音乐切换和循环 |

每个原型记录目的、运行方法、结论、是否采用和资源许可。被采用后，将成果整理进入正式美术、数值或程序模块，不能长期让生产代码依赖实验原型。

区分：

- 参考图或下载模型：`research`。
- 验证比例与玩法的灰模：`prototypes\3d`。
- 正式制作中的舰船：`art\models\ships`。
- 已审核并可加载的模型：`content\assets\ships`。

“下载完成”不等于“制作完成”，更不等于“允许发布”。

## 4. 美术与3D资产

### 4.1 单个舰船资产

```text
art\models\ships\yamato\
├─ source\                       # Blender等制作工程
├─ textures\                     # 与该舰相关的贴图制作源
├─ exports\                      # 审核用导出，不直接成为发布真值
├─ previews\                     # 预览、对照和审查图
└─ asset-info.json               # 资产ID、来源、许可、阶段与制作说明

content\assets\ships\yamato\
├─ ship.glb                      # 游戏加载的模型
├─ rig.json                      # 炮位与模型节点映射
├─ manifest.json                 # 尺寸、单位、LOD与资源引用
├─ LICENSE.txt
├─ source.json
├─ lod1.glb                      # 有需要再生成
└─ lod2.glb
```

原始收集的 STL、3MF、ZIP 继续保留在研究区，不因采用某模型就自动把原始下载签入。正式加工工程可通过来源引用关联原文件，保留原始文件不变。

### 4.2 按领域分工

- `concept`：舰船外形、港口、场景和氛围概念设计。
- `models`：舰船、武器、飞机、环境和道具。
- `materials`：可复用材质与制作工程。
- `textures`：跨资产共享的纹理制作源。
- `animations`：需要独立维护的动画制作工程。
- `vfx`：火花、烟雾、水花、尾迹等制作源与实验输出。
- `ui`：界面、图标、仪表和字体制作源。
- `marketing`：宣传图、展示截图、商店图和视频制作材料。

单舰专属贴图留在对应资产目录，共享贴图放在共享目录，避免复制出多份无法判断真值的文件。

### 4.3 格式约定

| 类型 | 制作源 | 运行资源 |
|---|---|---|
| 3D模型 | `.blend`及获准使用的原始格式 | `.glb` |
| 纹理和UI | `.kra`、`.psd`、`.svg`等 | `.png`、`.webp`，有需要时 `.ktx2` |
| 特效 | 制作工程、原型与参数 | 贴图、模型及运行参数 |
| 宣传材料 | 图片或剪辑工程 | 发布图片、视频，不混入游戏包 |

最终格式取决于运行环境和验证结果，不因为某种扩展名被允许就自动把文件发布。

资产单位、坐标、原点、节点、材质和LOD遵循模型规范。模型尺寸可以用于离线校验，不能让视觉模型隐式成为战斗参数的唯一来源。

## 5. 音乐、音效与语音

### 5.1 分类

- `music`：主菜单、港口、战斗、紧张段落、胜利和失利音乐。
- `sfx`：主炮、鱼雷、命中、爆炸、机械和界面反馈。
- `ambience`：海浪、风、港口和舰桥环境声。
- `voice`：指令、警告和播报；未制作时不创建假资源。

每个音乐或音效资产使用稳定ID，与文件名和播放场景解耦。

```text
audio\music\battle-theme\
├─ source\                       # DAW工程、原创MIDI与录音
├─ exports\                      # 审核用WAV等
└─ asset-info.json               # 来源、许可、阶段、循环与制作说明

content\assets\audio\music\
└─ battle-theme.ogg              # 格式依浏览器兼容性确认

content\data\audio\
└─ cues.json                     # 场景、音轨、循环与总线映射
```

运行包只带需要播放的资源与必要许可，不带 DAW 工程、插件缓存和全部录音。

DAW可使用 Reaper、Ableton、FL Studio或其他工具，不把目录规范绑定到某个软件。源音频可保留 WAV/FLAC，运行格式按兼容性与体积选择。

下载音乐与音效先进入研究区。免费试听不代表可分发；未确认授权的音频不能进入正式运行清单。录音、字体、纹理和模型遵循同样的许可边界。

当前游戏没有完整声音系统，本规范不代表音乐或音效已经制作或接入。

## 6. 数值设计

### 6.1 文档、编辑源和运行数据分开

| 位置 | 职责 |
|---|---|
| `docs\game-design\balance.md` | 设计目标、公式含义、推导与版本决策 |
| `research\historical-data` | 官网表格、历史资料和原始事实 |
| `design-data\source` | 可审阅的数值编辑输入 |
| `design-data\experiments` | 候选参数、对比配置和试验 |
| `design-data\reports` | 自动试算、曲线、统计与评估结果 |
| `content\data` | 经过校验、游戏实际读取的数据 |
| `src`中的模拟模块 | 有版本的公式实现 |
| `tools\data` | 转换、分析、生成与校验工具 |

默认以 CSV 作为数值发布流程的编辑输入。Excel/LibreOffice可以用于编辑，但每套表必须声明唯一权威编辑源；其他形式是导出或报告，不能手工双向维护两套真值。

### 6.2 推荐数值主题

- 舰船：耐久、尺寸、推进、转弯和能力。
- 武器：安装限制、转速、装填、射界和炮口参数。
- 弹药：弹种、伤害、穿甲、散布或弹道参数。
- 护甲：区域、厚度、材质和防雷设定。
- 任务：参战配置、出生、目标和难度。
- 成长：后续等级、维修、补给和奖励，未实现时保持明确状态。

单位、来源、已知/未知、自研换算和适用规则版本必须随数值维护。

数值试算尽量调用正式模拟中的同一套公式，不再在表格、分析脚本和游戏内各写一套未经验证的伤害算法。

运行 JSON 可由数值源生成，也可对特定内容采用直接 JSON 编写，但必须声明该文件的来源和权威编辑位置，禁止直接修改生成结果后让下次构建覆盖。

## 7. 程序、工具与测试

### 7.1 程序

当前继续采用根目录下的 `src`，不为了目录美观把整个工程立即搬入新的 `game` 子目录。程序内部按照架构规划划分应用、领域、模拟、表现、界面、输入和适配器。

不创建暂时没有实际功能的服务器目录。未来确定联机实现时再增加服务器工程和网络适配器，复用模拟内核。

### 7.2 工具

- `tools\data`：原始资料转换、数值试算、Schema和引用校验。
- `tools\models`：模型导入、坐标规范化、炮位检查、减面和导出。
- `tools\audio`：音频转换、循环与元数据检查。
- `tools\packaging`：运行清单、许可核对、打包和构建报告。

原型验证“方案是否可行”，工具负责“可重复地处理正式输入”，两者不混在一起。

### 7.3 测试

测试分别覆盖模拟行为、内容完整性、模块集成、界面、资源契约和性能。夹具保持小型、合法、可复现。

正常构建和核心测试不能依赖未签入的研究资料。只有明确标注的离线导入测试才可以要求本地原始素材。

人工测试步骤与验收要求写在 `docs\qa`，自动化代码放在 `tests`，失败日志和性能采样不混进源码目录。

## 8. 研究、缓存、构建与发布

### 8.1 研究区

`research`保存原始参考、手册、截图、历史数值和下载文件，保持来源和许可记录，不作为运行资源目录。

`pending-license`集中隔离授权未确认的模型、图片、声音和字体，不分散藏在正式资产目录中。

只有审核通过后，经过加工或必要转换生成允许使用的运行资源；原文件仍保持原样。

### 8.2 生成目录

| 目录 | 职责 | 是否作为编辑源 |
|---|---|---|
| `cache` | 可重建的转换缓存、中间文件与工具临时输出 | 否 |
| `dist` | 当前 Vite生成的部署内容 | 否 |
| `builds` | 内部测试构建、构建日志与验证报告 | 否 |
| `releases` | 发布候选、正式包、校验值、许可与发布记录 | 否 |

这些目录不作为普通源码提交。正式包通过发布存储或发布系统分发，发布说明可单独纳入文档管理。

用户存档、浏览器缓存和以后桌面版的用户数据不放进这些项目目录。

## 9. 命名与资产记录

目录和文件使用小写英文、数字与连字符，避免中文路径、空格和反复叠加的 `final-final-new`。中文用于文档标题、说明和本地化显示。

示例：

- 舰船目录：`yamato`、`bismarck`。
- 音频：`main-gun-fire.ogg`、`battle-theme.ogg`。
- 文档：`core-loop.md`、`model-standard.md`。
- 构建标识：版本号加构建ID，不作为日常源文件命名方式。

稳定资产ID与文件路径分开。重命名文件时更新资源清单与引用，不依靠文件名猜测资产身份。

`asset-info.json`建议记录：

- 资产ID、类别、公开署名和来源引用。
- 许可标识、许可链接与分发范围。
- 制作阶段：原型、制作中、待审、通过或停用。
- 源文件位置、导出目标和工具说明。
- 模型匹配程度、修改记录、单位与关键约束。

不存密码、令牌、私人联系方式或授权邮件全文。需要保密的材料在私有管理空间保存，项目只引用必要的公开结论。

## 10. 版本管理与公开边界

| 内容 | 当前公开仓库建议 |
|---|---|
| 程序、工具、自动测试 | 纳入版本管理 |
| 可公开的企划和设计文档 | 纳入版本管理 |
| 规范化数值与运行数据 | 纳入版本管理 |
| 审核通过、允许分发的运行模型与音频 | 按清单纳入，保留署名和许可 |
| 研究手册、截图、原始下载、待授权资源 | 不签入、不发布 |
| 美术工程、DAW工程和大量原始录音 | 当前默认不进入公开仓库，另行确认管理方式 |
| 私有商务、合同、个人资料和非公开邮件 | 不进入公开仓库 |
| 缓存、日志、内部构建和发布包 | 不作为普通源码提交 |

大量制作源资产可以使用私有资产库或在确认后使用 Git LFS；不能为了“标准目录”自动改变现有公开范围。

文件所在目录不是授权证明。扩展名是 GLB、PNG或 Ogg也不是允许发布的理由。发布必须同时满足实际使用、来源与许可审核、资源契约和明确清单。

本规范只新增文档，不立即调整 `.gitignore`、安装 Git LFS、创建私有仓库或移动现有资料。

## 11. 内容进入游戏的标准流程

```text
企划与玩法需求
      ↓
原型验证
      ↓
研究来源 / 原创制作 / 许可审核
      ↓
美术、音频制作源 / 数值编辑源
      ↓
工具转换与内容校验
      ↓
content：运行数据、资产、许可和清单
      ↓
src：游戏加载与模拟 / 表现
      ↓
测试与验收
      ↓
dist / builds / releases
```

项目不应同时维护“美术导出文件”“程序手工拷贝文件”“发布目录修改文件”三套无法追踪的真值。运行资源来自明确输入和加工流程；生产包由清单生成。
