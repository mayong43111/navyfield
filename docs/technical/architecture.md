# 单机海战游戏架构规划

日期：2026-11-22  
状态：阶段一单舰数值内核与本地会话已实施；其余为目标设计与迁移规划，尚未整体实施。

## 1. 项目定位与设计原则

项目定位为以舰船配装、舰队战术和海战模拟为核心的单机游戏。保留海战 II 风格的操作与界面，优先完成可验证、可保存、可扩展的单机闭环；当前不实现登录、匹配或网络对战。

继续使用 TypeScript、Vite 和 Three.js。Three.js 是表现层，不是战斗规则的载体。未来联机通过替换战斗会话适配器、把模拟内核运行在服务器上接入，不以重写客户端为前提。

核心原则：

1. 战斗模拟与输入、界面、渲染和存储分离。
2. 舰型定义、舰船实例和舰船模型使用不同 ID。
3. 游戏数值不由模型外形或界面布局决定。
4. 原始资料、规范化游戏数据和可发布资源分开管理。
5. 数值来源、单位、自研换算和未知项明确标记。
6. 模拟采用固定时间步；镜头、帧率和特效不改变战斗结果。
7. 初期使用简单实体集合与明确顺序的系统函数，不提前引入完整 ECS、复杂插件框架或大型事件总线。
8. 先保留现有行为完成架构迁移，再通过新的规则版本调整玩法和尺度。

## 3. 游戏整体流程与范围

### 3.1 单机流程

```text
主菜单 / 继续游戏
        ↓
港口：舰船、配装、补给、编队
        ↓
世界战区：选择任务
        ↓
出击准备：选择舰队、阵型、旗舰
        ↓
加载与建立战斗
        ↓
战场：玩家控制旗舰，其他舰船由 AI 执行命令
        ↓
结算：战果、损失、任务进度
        ↓
返回港口
```

世界地图是任务选择入口，不是持续运行的 MMO 世界。界面可以保留海战 II 风格，但单机内部不需要真实的多人房间、加入人数或等待其他玩家 READY。

### 3.2 首版核心玩法

- 舰型选择、每艘舰独立配装和编队配置。
- 玩家控制一艘旗舰，多艘友军与敌军实际参战。
- 航线、转舵、编队保持、避碰、目标分配、集火与撤退。
- 主炮射界、炮塔转速、装填、弹仓、弹种、弹道、散布、命中和毁伤。
- 任务胜负条件、统计与结算。
- 暂停、时间加速、存档、读档和回放。

鱼雷、航空、潜艇、船员、损管深化和复杂经济系统按阶段增加。未实现能力应明确禁用，不能用战列舰主炮冒充航空母舰攻击，也不能把防雷装甲当作万能护盾。

### 3.3 保持的操作边界

第一阶段保留当前操作：左键锁定海面瞄准点，右键设置航线，空格齐射，F/V 调整动力，A/D 转舵，Ctrl/TDA 控制炮塔转动加速，边缘滚屏，C 返回本舰。

输入映射负责把按键或鼠标转换为游戏命令。模拟内核不认识浏览器键码、屏幕像素或 DOM 元素。

## 4. 总体分层与依赖方向

```text
输入、界面、任务流程
        │ 玩家命令
        ▼
   BattleSession
        │
        ▼
独立战斗模拟内核 ← 规范化内容定义
  ├─ 世界与舰船状态
  ├─ 航行、编队、AI
  ├─ 炮控、弹药、弹道
  ├─ 碰撞、毁伤、感知
  └─ 任务、统计、结算
        │
        ├─ 只读观察状态 → 界面、镜头、舰船表现
        ├─ 战斗事件     → 火花、水花、音效、日志
        └─ 模拟快照     → 存档、回放
```

依赖约束：

- `domain` 定义数值类型、ID、内容契约、命令、事件和状态，不依赖外部环境。
- `simulation` 依赖领域契约和数值计算，不导入 Three.js、DOM、浏览器存储或原始资料加载器。
- `game` 管理港口、舰队、配装和进度，不直接操作场景对象。
- `presentation` 和 `ui` 消费观察状态与事件，不直接修改模拟状态。
- `adapters` 实现内容加载、存储和战斗会话，不把环境依赖倒灌进模拟内核。
- `app` 协调流程、资源生命周期与各层连接，不重新成为业务逻辑聚集地。

内核可以在内部更新其拥有的状态；对外提供只读、可序列化的数据边界。“纯数值”不意味着每一步都必须深拷贝整个世界。

## 5. 模块划分

| 模块 | 主要职责 | 关键输入与输出 |
|---|---|---|
| 应用流程 | 主菜单、港口、准备、加载、战斗、结算切换 | 流程状态、会话生命周期 |
| 内容系统 | 加载和校验舰型、装备、任务、规则、资源清单 | 内容包、完整性报告 |
| 港口与舰队 | 舰船实例、配装、泊位、编队与出击校验 | 玩家存档、出击配置 |
| 战斗会话 | 建立战斗、接收命令、暂停、加速和结束 | 命令、观察状态、事件 |
| 世界状态 | 管理舰船、武器、炮弹、阵营和生命周期 | 实体集合、稳定实体 ID |
| 航行系统 | 推进、加速、转舵、航线和避障 | 每舰运动参数、航行状态 |
| 编队系统 | 相对位置、间距、跟随、队形调整和避碰 | 编队命令、单舰航行意图 |
| 武器系统 | 炮控、射界、转速、装填、弹仓和齐射 | 武器定义、开火结果 |
| 弹道与碰撞 | 运动、散布、连续碰撞、命中与落水 | 数值碰撞体、候选命中 |
| 毁伤系统 | 护甲区域、防雷、损坏、沉没与击沉归属 | 命中记录、伤害和状态变化 |
| 感知系统 | 发现、跟踪、最后已知位置与可见信息 | 世界状态、阵营观察 |
| AI | 舰队决策、单舰机动、目标分配、炮控和撤退 | 感知信息、与玩家共用的命令 |
| 任务系统 | 胜负、护航、撤退、战斗统计与结算 | 任务定义、战斗结果 |
| 表现系统 | 舰船姿态、海面、镜头、仪表、特效和音效 | 观察状态、表现事件 |
| 存档与回放 | 保存、恢复、版本迁移和回放记录 | 完整模拟快照、命令记录 |

### 5.1 核心对象

- `ShipDefinition`：舰型参数、能力、炮位和装备限制。
- `OwnedShip`：玩家拥有的舰船，独立名字、配装和维护状态。
- `FleetDefinition`：舰队成员、旗舰、角色和相对阵位。
- `BattleConfig`：出击时冻结的任务、规则、配装、出生配置和随机种子。
- `WorldState`：全部参战实体的运行状态，不固定为两个对象。
- `ShipState`：位置、航速、航向、耐久、损坏、阵营和生命周期。
- `WeaponState`：炮控角度、装填、弹仓和开火状态。
- `ProjectileState`：类型、位置、速度、发射信息和生命周期。
- `Observation`：某一阵营或玩家可看到的信息。
- `BattleEvent`：开火、命中、落水、损坏、沉没、拒绝命令和任务变化。
- `BattleResult`：任务结果、舰船损失、伤害统计和规则标识。

出击时复制并校验配装，冻结内容定义。港口里的配装修改不能影响已经建立的战斗。

## 6. 海战模拟设计

### 6.1 2.5D 模拟与3D表现

首版不做完整舰船刚体和浮力求解：

- 舰船在海面平面航行。
- 炮弹有三维位置和高度。
- 舰体使用数值化的简化碰撞体。
- 海浪、轻微摇摆、炮管后坐首先属于表现效果。

如果以后摇摆、风浪或浮力会影响命中，必须作为明确的模拟系统实现，不能让模型动画隐式改变规则。

### 6.2 时间与随机数

建议初始模拟频率为30次/秒，渲染按设备能力运行，并对相邻模拟状态插值。AI决策可低于模拟频率；具体频率由性能测试确认，不作为已达成指标。

每个模拟步按稳定顺序：

1. 收集玩家和 AI 命令。
2. 校验并应用命令。
3. 更新航行、航线和编队。
4. 更新炮控、装填和开火。
5. 推进弹道并检测连续碰撞。
6. 统一处理命中、毁伤和沉没。
7. 更新感知、任务与统计。
8. 输出观察状态和事件。

AI使用最近完成的感知结果决策，输出的命令经过与玩家相同的校验。事件需要稳定 ID 和顺序；同时命中与相互击沉不能因舰船遍历顺序而偏向某一方。

战斗随机数使用可保存状态的种子生成器。特效使用独立随机源；增加烟团或水花不能改变炮弹落点。

单机暂停时停止模拟时钟。时间加速推进更多固定模拟步，不修改舰速、装填或弹道参数。卡顿时采用有明确策略的追帧、减速或暂停，不通过静默丢弃模拟时间跳过炮弹。

### 6.3 航行、编队与出生

舰长、舰宽、推进与转向能力应影响碰撞、航线、间距和队形保持。首版先采用可解释的游戏运动模型，不宣称已实现完整水动力学。

阵型保存编队中心、朝向、每舰相对位置、角色和间距。准备页分页和格子只是编辑表现，不参与战场坐标计算。出生完成后校验边界与舰体重叠。

已有“左右各两个出生区、间隔至少为最大射程10倍”的要求作为任务出生规则保留。按双方实际配装和适用规则的射程上界预计算，不由模型或准备页阵位推算。

若未来采用真实尺度，这个间隔可能使接敌耗时很长。应使用明确的单机时间加速或任务阶段设计；改变出生规则必须单独确认，不能偷偷缩短距离。

### 6.4 炮控、弹道与毁伤

- 炮位位置、射界、水平与俯仰转速属于游戏数据。
- 开火检查装备、弹种、装填、弹药、射界、转炮和弹道可达性。
- 每根炮管独立产生炮弹与散布样本。
- 散布、弹道和毁伤算法属于有版本的规则，不标称为未经核实的官方公式。
- 炮弹与运动舰体使用连续碰撞，避免高速炮弹跨过舰体。
- 碰撞判定不使用渲染网格或 GPU 拾取。
- 大量实体时可引入空间索引缩小候选碰撞集合，先测量再优化。
- 护甲按区域、厚度与材质表达；数据不足时保留明确标注的简化算法。
- 防雷装甲与主炮护甲分开，鱼雷系统未实现前不伪造其战斗作用。

命中、毁伤与特效分离。内核确定结果，表现层消费事件生成火花、燃烧、水花和沉没动画。

旗舰沉没是否失败、是否允许换舰、撤退是否完成任务，由任务定义决定，不在内核写死所有战斗都以“本舰归零”结束。

### 6.5 感知与地图

区分真实舰船、已发现目标、追踪目标和最后已知位置。首版可以采用简单视距，后续增加雷达、侦察机、烟幕和天气。

AI不能默认永远知道所有敌舰坐标。界面和 AI 应消费对应阵营的观察信息。

世界地图与战术地图分开：当前粗粒度世界海岸 GeoJSON 适合任务导航，不适合直接作为战斗岛屿碰撞数据。战术地图应明确边界、岛屿多边形、出生区、任务区域和必要高度数据。

## 7. 游戏数据与格式

### 7.1 四类数据

| 类别 | 内容 | 管理方式 |
|---|---|---|
| 内容定义 | 舰型、武器、弹药、护甲、装备、规则、任务 | 有版本、经过校验，战斗中不可变 |
| 玩家存档 | 拥有舰船、配装、编队、任务进度 | 可持久修改 |
| 战斗状态 | 坐标、航速、耐久、弹药、装填、炮弹、AI状态 | 内核拥有并更新 |
| 表现状态 | 镜头、粒子、菜单、选择、高亮和动画 | 不参与战斗判定 |

### 7.2 格式选择

| 内容 | 建议格式 |
|---|---|
| 舰型、武器、弹药、装备、规则和任务 | JSON |
| 数据结构与约束 | JSON Schema及对应 TypeScript 类型 |
| 原始资料整理与人工对照 | CSV、原始 JSON，仅研究使用 |
| 战术地图 | JSON，包含边界、多边形、区域和高度信息 |
| 世界地图 | GeoJSON |
| 文本与翻译 | 按语言划分的 JSON |
| 运行资源清单 | JSON，使用稳定资源 ID |
| 存档导出 | 带版本信息的 JSON |
| 回放记录 | JSONL，可选压缩 |

首版不需要数据库服务器或浏览器内 SQLite。存档的逻辑格式是可序列化数据；浏览器存储使用 IndexedDB，完整存档不放入 `localStorage`。

### 7.3 舰型与装备字段

舰型定义包括：

- 稳定 ID、原始来源 ID、名称键、国家和舰种。
- 舰长、舰宽、吃水与碰撞体。
- 耐久、护甲区域和能力。
- 推进、加速、转向参数。
- 炮位位置、方向、射界和装备限制。
- 传感器、航空设施等能力。
- 默认配装、模型引用与匹配说明。
- 数值来源、单位、完整性和可用性。

武器定义包括类型、口径、管数、安装限制、炮口速度、最大仰角、水平与俯仰转速、装填、弹仓、弹种兼容性和散布规则引用。火炮、鱼雷管与航空设施使用各自的能力和约束，不强行套用同一套弹仓界面。

图鉴记录与可用能力分开。496条舰型资料、807条武器资料不代表相同数量的内容已经完整实现。数据完整性和模型匹配状态也分开：有完整玩法数据可以使用明确占位模型，缺少关键玩法数据则应禁用对应能力并说明原因。

### 7.4 来源与规范化流程

```text
官网 / 历史资料
      ↓
研究数据
      ↓ 离线转换、单位解释、人工确认
规范化游戏数据
      ↓ 结构、引用、配装和完整性校验
可发布游戏数据包
```

关键数值区分官网事实、历史资料、模型推导、自研设定和未知。来源与转换说明可以通过引用记录保存，不必把所有研究资料打进运行包。

未知不能默默填成0，也不能自动借用大和参数。经过明确标注的自研设定可以作为玩法数据，但不能显示为已核实史实。

结构错误、引用不存在、单位非法、装备超限和运行炮位缺失应明确报错。允许明确的未知事实，但可出击内容必须满足所用任务和规则的必要能力校验。

### 7.5 单位与规则版本

目标是明确采用米、秒、弧度等内部单位。界面可按模式显示距离和速度，但史实参数与实际游戏数值分开。

当前模型和战斗使用的游戏单位不能只通过改字段名宣称为米制。迁移时需要明确转换关系并验证视觉、碰撞、航行和弹道一致性。

第一阶段保留现有坐标约定和游戏规则，不立即改变航速、射程、朝向或显示单位。之后通过新规则版本讨论真实尺度与经典压缩尺度。规则记录适用单位、弹道、散布、毁伤、出生和补给策略。

坐标轴、航向零点、旋转正方向和模型前向必须统一记录；修改这些约定需要显式转换与回归验证，不能在资源加载器中零散补偿。

数据包应区分模拟内容标识与表现资源标识。仅更换纹理或视觉 LOD，不应使原本相容的战斗回放失效；改变炮位、碰撞、规则或任务则属于模拟内容变化。

## 8. 模型与其他资源

### 8.1 运行与加工格式

| 资源 | 运行格式 | 加工或原始格式 |
|---|---|---|
| 舰船、炮塔、飞机、地形 | GLB | STL、3MF、OBJ、FBX、Blender工程等 |
| 普通贴图 | PNG、WebP | 原始绘图工程 |
| 大量贴图 | 有需要时使用 KTX2 | 原始图片与转换输入 |
| 音效、音乐 | 按浏览器兼容性选择 Ogg、MP3等 | 原始音频与编辑工程 |
| 节点映射、资源清单 | JSON | 可由工具生成和人工校验 |
| 署名、许可、来源 | TXT、JSON | 保留来源记录 |

原始资料和加工工程不进入普通运行包。许可不明的模型继续隔离，等待授权，不进入可发布资源清单。

### 8.2 模型包

```text
yamato\
  ship.glb
  rig.json
  manifest.json
  LICENSE.txt
  source.json
  lod1.glb          # 有需要再生成
  lod2.glb
```

- `rig.json`：游戏炮位与炮座、俯仰、炮管、炮口等模型节点的映射。
- `manifest.json`：模型 ID、单位约定、尺寸、资源引用、LOD和匹配说明。
- 署名、许可和修改说明随模型分发。
- 同级参考、同源参考和占位外形明确标记，不宣称精确年份复原。

现有节点可以通过映射复用，不需要立即重命名全部模型。

### 8.3 模型与模拟的边界

游戏炮位和炮塔状态决定模拟炮口位置。开火、碰撞与射程计算不读取 Three.js 世界矩阵。

模型可以用于离线生成炮位初稿和尺寸校验，但发布时需要冻结为明确的游戏数据。模型节点与游戏炮位之间需要验证，避免炮弹从错误位置出现。

未匹配外形建议使用按舰长、舰宽和炮位生成的灰模，减少小舰全部显示成大和造成的视觉与碰撞偏差。该策略属于后续迁移，不立即替换现有占位外形。

按港口选择、任务和舰队需要加载模型，不在启动时加载整个舰船库。几何和材质共享，炮塔姿态与舰船状态独立。LOD、对象池、批量特效和资源释放由表现层管理。

大型战场如需相机相对渲染原点，只调整表现坐标，不因镜头移动修改模拟世界坐标。

## 10. 存档、回放与离线

### 10.1 存档

存档至少包含：

- 格式版本、模拟版本、规则版本与模拟内容标识。
- 玩家舰船、配装、编队和任务进度。
- 当前战斗配置与必要世界状态。
- 模拟时刻、随机数状态和待处理命令。
- 恢复所需的装填、弹药、航线、AI和任务状态。

不保存 Three.js 对象、DOM、GPU资源或粒子对象。镜头等偏好可以独立保存，不作为战斗判定依据。

IndexedDB负责本地存储，JSON用于导入导出。读档先校验版本和引用，再恢复模拟；不兼容时明确提示或通过已定义迁移处理，不能静默重置。

结算以战斗 ID 记录应用状态，避免重复读档或重复提交导致任务结果多次应用。

### 10.2 回放

记录初始战斗配置、随机种子、带模拟时刻的命令，以及必要校验点和快照。快照支持定位与兼容性检查，事件可辅助诊断和表现。

同版本、同内容和受支持运行环境下应验证可复现性，不承诺不同版本或不同环境的浮点计算永远逐位一致。规则或模拟内容不相容时明确拒绝或使用对应版本，不能用当前数值悄悄播放旧战斗。

### 10.3 离线与分发

- 本地静态包可以完全离线运行。
- GitHub Pages是分发渠道，不是战斗服务器。
- 网页首次加载仍需要获取代码和资源；后续可增加资源缓存和离线支持。
- 离线缓存应按内容版本管理，避免旧数据与新代码混用。
- 桌面封装复用同一套内核与内容，不重新实现规则。

## 11. 未来联机预留

### 11.1 现在只预留会话边界

`BattleSession` 向应用提供发送命令、订阅观察状态与事件、查询会话状态和结束会话的能力。暂停与加速是单机会话能力，不假定所有未来会话都支持。

```text
单机：
输入 → LocalSession → 本地模拟 → 观察状态 / 事件

未来联机：
输入 → NetworkSession → 网络 → 服务器模拟
                           ↓
界面 ← 观察状态 / 事件 ← 网络
```

当前不建立空的网络框架、登录系统或服务器工程。先验证内核能在无 DOM、无 WebGL 的环境运行。

### 11.2 服务器复用与权威边界

服务器复用内容定义、航行、编队、AI、武器、弹道、碰撞、毁伤和任务系统，不需要模型、纹理或镜头。

客户端发送航点、动力、转舵、瞄准点、弹仓、开火和编队命令，不发送“已经命中”或“应该扣多少血”作为真值。

服务器决定命令适用时刻、装填、弹药、散布、命中、伤害和结算。未来还需校验舰船控制权、命令顺序、配装及规则版本。

### 11.3 同步策略

优先采用服务器权威状态，不以跨平台确定性锁步为前提：

- 对自身航行做有限预测，对其他舰船插值显示。
- 使用序号、模拟时刻和确认信息处理命令与校正。
- 炮弹可根据发射事件和轨迹参数表现，最终命中以服务器事件为准。
- 观察状态和事件按接收者的可见信息过滤，不向每个客户端发送所有未发现敌舰的完整状态。
- 客户端后台、卡顿或断线不暂停服务器战斗。

具体传输方式、同步频率、量化和重连协议在实际联机阶段按规模与测量结果选择。

单机存档允许本地导入导出，但不能直接成为联机舰船、货币、等级或成绩的权威来源。联机进度与规则需要独立的服务器管理。

## 12. 分阶段迁移与验收

### 阶段一：抽出模拟内核

已落实的运行边界（2026-11-22）：

- `src/domain/battle.ts` 定义 ID、数值配置/状态、命令、事件、冻结观察及 `BattleSession` 契约。
- `src/simulation` 不导入 Three、DOM、存储或原始资料加载器；以 30Hz 固定步推进现有单舰导航、炮控、AI、弹道、碰撞、毁伤与结算，种子随机数由战斗单独持有。
- `src/adapters/local/battle-session.ts` 实际连接输入命令与观察/事件；命令按模拟步排队，外部不能修改会话状态。后台暂停，可见页面卡顿补齐全部时间。
- `battle-config.ts` 在出击边界复制旧资料数值、碰撞尺寸、炮位/炮口与配装，内核自行深拷贝校验并冻结。每帧模型摇摆、炮口节点、镜头和特效不再反馈到模拟。
- `main.ts` 仅启动；`app/controller.ts` 在无 DOM/Three 环境管理页面和会话生命周期，`app/runtime.ts` 组合资源、适配器、界面、输入和时钟。
- `game/port-controller.ts` 独占港口舰艇/配装，以命令和冻结观察连接界面，出战后仅在退出边界显式接收战斗弹仓。配装内容校验由 `adapters/local/port-content.ts` 注入。
- `input` 分离键盘与画布/海图指针；`ui` 分离弹仓、船坞、操作按钮、投影标签和仪表；`presentation/battle-view.ts`、`environment.ts`、`battle-effects.ts` 仅处理图形、镜头、模型和特效。界面不直接修改模拟或港口状态，旧跨层屏幕协调器已删除。旧顶层导出及资源加载模块仍保留兼容路径。

这不是全部目标架构完成：建立新战斗时炮位仍通过模型契约适配器取得，尚未离线规范化为独立内容定义。旧资料加载、模型创建、共用界面辅助函数暂留兼容路径。准备页仍不产生整支参战舰队，原分页阵位映射仅为保留现有单舰规则。未增加存档、回放、联机、ECS 或新平衡。

- 定义领域 ID、命令、事件、战斗配置和状态。
- 抽离现有导航、弹仓、炮控、弹道、碰撞、AI与结算数值逻辑。
- 引入固定时间步和独立战斗随机数。
- 用单机会话连接输入和表现。
- 保留当前单舰规则、操作、数值和效果，不同时调整游戏平衡。

验收：

- 内核能在无 DOM、无 Three.js 场景的测试环境运行。
- 相同命令、种子与模拟版本下，改变渲染帧率不改变结果。
- 移动镜头、关闭特效或替换同契约的模型不改变模拟结果。
- 现有相关回归测试继续通过。

### 阶段二：规范化数据与资源

- 离线转换原始舰型、武器、弹药和护甲资料。
- 明确单位、来源、未知项、规则和内容版本。
- 数据化舰型映射、炮位与模型节点契约。
- 建立运行资源清单，保持原始资料与许可不明资源排除。

验收：

- 游戏不再在战斗过程中解释原始表格字符串。
- 引用、单位、配装限制、炮位及可用能力可以校验。
- 更换视觉资源不隐式改变碰撞、射程或炮座数量。
- 缺失与占位状态在界面上明确显示。
- 新克隆得到允许发布的运行资源后可以构建和测试。

### 阶段三：完成舰队战斗

- 整支出战舰队生成独立舰船与武器状态。
- 阵型变为相对世界位置，加入保持队形与避碰。
- 友军与敌军 AI 使用相同命令和武器校验。
- 加入基础感知、目标分配与任务条件。

验收：

- 准备页每艘出战舰实际参战，弹药和耐久互不串用。
- 分页与界面缩放不改变出生位置。
- 出生满足所选规则且舰体不重叠。
- 同时击沉和任务结算不依赖实体遍历顺序。
- 在定义的舰船、炮弹和模型规模下测量模拟与渲染性能。

### 阶段四：完成单机闭环

- 保存与恢复港口、编队、任务和战斗。
- 记录命令、快照与回放。
- 明确暂停、加速、后台与离线资源策略。
- 处理内容和存档版本升级。

验收：

- 战斗中读档正确恢复弹药、装填、航线、随机数与任务状态。
- 同版本回放能复现受支持环境下的战斗结果。
- 结算不会重复应用。
- 离线运行不依赖游戏服务器。

### 阶段五：扩展海战能力

按独立功能逐项增加鱼雷、航空、潜艇、感知深化、损管、船员和经济。每项同时完善定义、模拟、AI、表现、存档和测试，不能只加入模型与按钮。

具体新规则、操作和未确定行为在实施前确认，不以本规划代替玩法决策。

### 未来阶段：联机

实现服务器会话、网络适配器、权威进度、观察过滤、同步和重连。验收重点是复用内核，而不是把客户端状态直接上传或维护第二套战斗算法。

2. 规范化数据，分清定义、实例、模型与规则。
